## 1. 问题定义

### 1.1 Agent 出错之后，没人说得清它到底经历了什么

传统软件出错有调用栈、日志、断点和单元测试。Agent 的执行链路涉及模型、上下文、外部工具、环境状态与外部 API，
同一个输入不保证同一个输出。结果是：开发者通常只能看到**最终错误**，看不到它在第几步开始偏离正确路径。

### 1.2 待验证的差异是固定工具证据后的回归调试

LangSmith 和 Langfuse 已提供数据集、实验与评测，不能概括为只读平台。
本项目优先验证更窄的问题：能否在本地固定工具证据，重跑 Agent 决策，并明确区分断言失败与录制不足。
pi 作为第二条接入路径，首轮仅支持 SDK 只读代码调查，不宣称通用框架恢复能力。

官方能力参考：[LangSmith](https://docs.langchain.com/langsmith/evaluation-concepts)、[Langfuse](https://langfuse.com/docs/evaluation/get-started/offline)。

### 1.3 修改之后缺少系统化验证

改 Prompt、换模型、调工具之后，"变好了吗"目前只能靠重跑一遍凭感觉判断。
缺少的是：把生产环境里的失败固定成一条可重复执行的用例，拿到明确的通过或失败。

## 2. 产品定位

> **Replay, debug and evaluate AI agents like software.**

Agent 时代的 Debugger + Flight Recorder + Testing Platform。

它**不直接与任何 Agent 产品竞争**，而是服务所有 Agent。无论哪个框架成为主流，只要 Agent 要进生产环境，
观察、调试、验证、回放、评估这些需求就一直在。

### 不做什么

- 不做 Agent 框架，不做编排引擎。
- 不做通用 LLM 可观测性平台（trace 采集已经是红海，且被标准协议覆盖）。
- 不替用户评估模型好坏。平台给出差异事实，结论由用户下。

## 3. 目标用户

| 用户 | 他们负责什么 | 触发场景 | 他们最在意什么 |
| --- | --- | --- | --- |
| **Agent 开发者**（首要） | 用 LangGraph / OpenAI Agents SDK / 自研 Runtime 写 Agent | 线上 Agent 给出了错误结论，需要定位到具体哪一步 | 接入成本要低，回放要可信 |
| **AI Infra / 平台团队** | 维护 Agent Platform、AI Gateway、Prompt、Model Router | 换模型 / 改路由之后要证明没有引入回归 | 能不能批量跑、能不能给出可对比的证据 |
| **企业内部 Agent 团队** | Coding / SRE / 客服 / 金融 / Data Agent | 生产事故复盘，以及上线前的回归验证 | 副作用安全、数据不能出内网 |

本轮优先服务第一类用户：他们的痛感最直接，也是"出事之后才来找工具"的那群人。

## 4. 核心用户旅程

整个产品的价值压在这一条路径上：

```
失败运行  ->  时间线复盘  ->  从某一步回放  ->  改 Prompt 重跑  ->  对比定位分叉  ->  沉淀为用例
```

### J1 事后取证：这次到底哪里错了

开发者打开一条失败的运行，沿时间线逐步查看每一步的输入、输出、token 与耗时，
找到模型第一次做出错误决策的位置。**已交付。**

### J2 从某一步重跑：不用重放前面全部工作

长任务 Agent 跑一次可能要几分钟和大量 token。开发者选定第 N 步，只重跑 N 之后的部分。
分叉点之前的所有步骤直接复用录制结果，普通节点代码仍可能重新执行。**LangGraph 示例路径已交付；pi 仅支持从任务起点。**

### J3 改动验证：改完到底有没有变好

开发者切换 Prompt 版本或指定新模型，重跑同一条运行，然后打开对比视图查看：
工具调用序列是否一致、模型输出在哪里分叉、成本与耗时变化如何。**已交付。**

### J4 生产失败沉淀：把一次事故变成长期资产

把失败运行固定成一条带断言的回归用例。之后每次改动 Prompt 或模型，重跑用例就能拿到明确的通过或失败。**已交付。**

### J5 模型选型（下一阶段）

同一任务在多个模型上批量跑用例，横向对比结论与成本。批量矩阵与按条件分组的汇总**已交付**：
同一批可以换模型各跑一列，每个条件各自列出四态计数与可判断率，不存在跨条件的合成总分。
仍缺的是跨批次的历史趋势与成本对比视图，以及条件维度的自动展开（例如遍历全部候选模型）。

## 5. 能力范围

### 5.1 已交付

**Agent Run Recording**

- 完整记录模型调用、工具调用、状态快照、错误与运行边界。
- 每条事件带输入、输出、token、耗时、成本估算、副作用等级与结果来源。
- 通过 LangChain / LangGraph 中间件接入，接入成本是一行代码。
- 录制链路**永不向上抛异常**：录制失败不允许打断或拖慢被观测的 Agent。

**回放引擎**

- 两种语义：**复现**（全部使用录制结果）与**回归**（模型真实执行，工具沿用录制结果）。
- 单步策略覆盖：可以让指定的某一步真实执行，其余照旧。
- 副作用闸门：写操作与对外动作默认被拦截，放行需显式开关且留痕。
- 分叉检测：回放过程中在线判定第一个行为不同的步骤。
- **回放预算**：可声明最大成本（USD）与最大模型调用次数；上限在 SDK 层生效，提交前可预估，
  执行中在步边界硬停（不再发起新的模型调用），结束后给出「已用 / 上限 / 是否触顶」的对照，
  因触顶而停止判为 `inconclusive`（成因码 `budget_exceeded`），不是失败。

**Web 控制台**

- 运行记录列表（按 Agent、状态筛选，可标记对比）。
- 运行详情与时间线（逐步展开输入输出、属性、脱敏记录）。
- 回放面板（选起点、选模式、单步覆盖、Prompt / 模型覆盖、副作用开关）。
  可设预算上限、可看预估；回放结束后详情页展示实际用量与是否触顶，触顶明确显示为「因预算停止」。
- 差异对比（工具调用对齐、模型输出对齐、指标变化、首个分叉点）。
- 回归用例（创建、运行、断言结果）；Agent 可在 `AgentSpec.seed_cases` 里自带用例，播种时一并建出并跑一次。
- **批量运行与条件矩阵**：一次提交一组用例 × 一组条件（Prompt 版本 / 模型），后台执行、进度可查；
  汇总按条件分组给出四态计数与可判断率（分母是该条件自己的用例数，并写出「N 条中 M 条拿不到结论」），
  **不合成任何跨条件的总分**；单条用例失败不会拖垮整批，成因逐条可见。

**其他**

- 入库时脱敏：凭证、密钥、私钥块等按规则替换并留痕。
- SSE 实时尾随正在执行的运行。
- OTel GenAI 语义约定导出（只导出，不导入）。
- 端到端自检 `doctor()`：真实往返一次上报，而不是检查配置文件是否存在。

### 5.2 明确不在本轮范围

- TypeScript SDK（协议已冻结，加语言只是加客户端）。
- LLM Judge 与数据集版本管理。
- 批次级聚合预算（整批最多花多少、超了如何处置未启动的格子）；本轮只做单次回放的预算。
- 跨批次的历史趋势看板与成本对比图表（单批内的条件矩阵已交付，仍不给任何跨条件的合成总分）。
- 多用户、权限、团队协作、自部署编排。
- OTel 导入。

## 6. 关键产品决策

这几条是真正做过取舍的地方，也是这套东西区别于"又一个 trace 查看器"的原因。

### 6.1 Replay 必须拆成两种语义

"回放"在工程上是两件不同的事。混在一起会让成本、可信度和界面全部失焦，因此显式拆开，并成为界面上的两个按钮：

| 模式 | 模型 | 工具 | 回答的问题 |
| --- | --- | --- | --- |
| 复现 | 用录制结果 | 用录制结果 | 它从第几步开始偏离？ |
| 回归 | 真实执行 | 用录制结果 | 改完到底有没有变好？ |

回归模式下工具沿用录制结果不是偷懒：要比较的是推理与决策，如果工具数据同时漂移，两次运行就不可比了。

### 6.2 副作用闸门默认拒绝

回放会重新执行 Agent，因此"它可能再删一次 Pod"是必须回答的问题。
规则是**默认拒绝、显式放行、留痕可查**：写操作与对外动作在回放中强制降级为拦截，返回"本应做什么"的合成结果；
要真实执行必须同时设置策略为 live **且** 打开总开关，执行后写入高可见度的告警事件。

### 6.3 Checkpoint 不是独立能力

状态快照不需要单独一套机制。一次运行如果本身就是一条 append-only 的事件日志，步边界可作为观察位置；是否能够恢复执行仍取决于框架状态和适配器。
把它做成并列的独立能力，会导致"存状态快照"与"从日志重放"两套状态模型并存，是最难还的架构债。
因此：状态快照在步边界自动记录，框架原生的 checkpoint 标识只作为引用保留，需要时由框架自身能力恢复。

### 6.4 只做确定性断言

引入 LLM Judge 会带进第二个不确定性来源，而当前要证明的是"失败案例可以被**稳定**复现与验证"。
因此断言全部是确定性的（结论包含 / 不包含 / 正则、工具是否调用、参数匹配、调用序列、调用次数上限、无错误）。
LLM Judge 属于下一阶段，且必须与确定性断言分开呈现。

### 6.5 条件标签是一等字段

同一条断言在不同条件下结论不同，这不是 bug 而是事实。
用例因此显式记录回放起点、模式、模型与 Prompt 版本；对比视图也只给差异事实与方向提示，不合成总分。
把不同实验条件下的数字加总成一个分数，是评估体系里最容易把可信度毁掉的做法。

## 7. 竞品与差异化

| 类别 | 代表 | 它们强在哪 | 本项目的差异 |
| --- | --- | --- | --- |
| LLM 可观测性平台 | Langfuse、LangSmith、Phoenix、Braintrust | trace 采集成熟、生态广、开箱即用 | 已有实验与评测；本项目验证本地工具证据回归与明确的不可判断结果 |
| 框架自带调试器 | LangGraph Studio 等 | 与框架深度集成 | 深度恢复依赖框架；本项目按适配器声明支持范围 |
| 评估平台 | 各类 eval 工具 | 数据集与打分体系完整 | 本项目从"生产失败"这个源头进，而不是从"造数据集"进 |

诚实的判断：**记录能力本身已经完全商品化，是入场券而不是卖点。**
本项目的真正差异在回放：可复现的执行、副作用可控、改动可验证。

## 8. 成功标准

对外展示型 MVP 的验收标准是"别人克隆下来能自己跑通这条闭环"，而不是功能数量。

**端到端验收（已通过自动化测试覆盖）**

1. 一键启动后，能看到 seed 运行的完整时间线，以及 Agent 自带的那条用例（开局即失败）。
2. 从某一步以复现模式回放，结论与原运行逐字一致（确定性）。
3. 换上修正版 Prompt 以回归模式重跑，结论发生改变。
4. 对比视图指出第一个不同的步骤，且工具调用序列显示为完全一致。
5. 写类工具在回放中默认被拦截并留下告警标记；显式放行后才真实执行。
6. 自带用例与手动把失败运行转成用例走同一条链路：默认 Prompt 下失败，修正版 Prompt 下通过。

**质量门槛**

- 复现模式的确定性有专门的测试守着，它是回放可信度的地基。
- 录制链路的失败不影响业务逻辑，有测试证明上报失败不会向上抛异常。
- 副作用闸门有测试证明默认拦截、显式放行两条路径都正确。

## 9. 风险与未解问题

| 风险 | 说明 | 当前应对 |
| --- | --- | --- |
| **精确复现并非总是可能** | provider 会下线模型版本、alias 会指向新权重 | 把这条写进回放语义文档；需要精确复现时用复现模式 |
| **回放成本不可控** | 大量用例 × 大 context 是实打实的 token 支出 | **单次回放已可预算**：可声明最大成本与最大模型调用次数，提交前可预估，执行中在步边界硬停，结束后如实记账（触顶判为 inconclusive，成因码 `budget_exceeded`）。**剩余边界**：批次级聚合预算（整批上限、超限后未启动格子如何处置）尚未做，是下一步；价格表仍是本地快照，所有数字都是估算 |
| **工具结果漂移** | 即便工具结果是录制的，外部世界已经改变 | dry_run 返回的是"本应做什么"，不是"当时做了什么"，文档中明确声明 |
| **录制管线静默失效** | 上报失败被吞掉，界面上看不出异常 | 暴露 `stats.last_error` 与健康标志，并提供真实往返自检 |
| **接入面只验证过一个框架** | 目前只有 LangGraph 的真实被测对象 | 回放核心与框架适配层分离，但第二、第三个框架的接入尚未验证 |

**未解问题**

- 长任务回放的中间状态该不该落盘？现在全部在内存里，超大运行可能吃紧。
- 用例的"部分通过"如何表达？当前区分 passed / failed / inconclusive / error，不把缺失证据合并为失败。
- 前端对比视图在两条运行步骤数差异很大时，对齐结果的可读性会下降。

## 10. 当前路线

1. 修复回放契约：所有 live 工具路径经过副作用闸门；录制不足不能判通过。
2. 用 pi SDK 只读调查固定 Git 提交，输出本地录制包并复用现有控制台。
3. 五个真实代码任务，两个 Prompt 各三次回归，以真实报告决定下一步。

暂缓通用 TypeScript SDK、其他框架、LLM Judge、多租户和排行榜。pi 运行器是专用适配器，不能代表通用 SDK 已完成。
如果多数样本因参数变化无法判断，优先研究固定仓库快照上的只读工具重执行。

实际验证状态见 [pi 验证记录](pi-validation.md)：已用真实模型完成两轮对照。结论是回归时的工具来源必须放开（固定快照上重执行只读工具），否则 93% 的样本拿不到结论；同时这批任务区分度不足，baseline 已全部答对，尚未观察到 Prompt 带来的真实修复。
